# Create or continue an experiment

The skill instructions are in English. The bundled scaffold currently generates
Czech experiment documents, preserving the source workflow's language
convention; teams may adapt the scaffold to their working language.

Make every experiment understandable to the next agent without the chat that
created it. This skill is self-contained: **do not look for or copy** a separate
experiment template directory. The required rules, output templates, generator,
and validator are bundled here.

## One experiment, two views

Treat an experiment as one evolving research question, not as one immutable
folder snapshot and not as an archive of every generated byte.

- The **current view** is rewritten in place: `README.md`, `OUTCOME.md`, optional
  `STATE.json`, stable semantic files under `data/processed/`, and current code
  under `src/`. It contains only the best known state and the next useful step.
- The **evidence ledger** explains how that state was reached: `runs/INDEX.md`,
  compact run receipts, `DECISION.md`, and publication receipts. Run identities
  and original receipts are immutable; later authority or retention transitions
  record their reason and replacement. Superseded bulk payloads need not be
  retained forever.

Artifacts move through `working -> candidate -> current -> superseded ->
pruned`. There is at most one `current` materialization for one logical
artifact. Use a stable name and update it; never accumulate `v2`, `final`, or
`latest` siblings.

## Select the operating mode first

### Existing experiment

Treat the task as continuation when the user names an experiment or the current
directory (or a clear ancestor) is already an experiment with meaningful
`README.md` and `OUTCOME.md` files.

- Do **not** run the generator and do not create a sibling experiment merely
  because a new run or new evidence is requested.
- Read the applicable `AGENTS.md` or `CLAUDE.md`, then the experiment's
  `README.md`, `OUTCOME.md`, and `STATE.json` when present.
- Read `DECISION.md`, `runs/INDEX.md`, `handoff/README.md`, or
  `handoff/PUBLISHED.md` only when they exist and matter to the current task.
- Establish the current question, phase, last verified state, next step, and
  blockers before changing anything. The skill carries the operating contract;
  the experiment files carry experiment-specific facts and current state.
- Load the detailed contract linked below only for the part of the lifecycle
  being changed. Perform the requested work, update the canonical document that
  owns the result, and run the validator before handoff.
- Preserve run identity, original provenance, result, and publication receipts.
  Authority and retention may change only as an explicit recorded transition;
  never rewrite old evidence to make a new result look canonical. Superseded
  run payload may be compacted or pruned only through the retirement gate in
  the detailed contract.

### New experiment

Create a new dated experiment for a new independent research question, a new
trial, or a materially different focus. A refinement of the same question, an
additional run, or new evidence belongs in the existing experiment instead of a
competing source of truth.

If a new experiment depends on an older one, create the new experiment and add
the older work as a real input only when it is actually consumed.

## Keep the framework separate from experiment workspaces

This repository distributes a method and its tools; it is not a user's data
workspace. When creating an experiment while the current directory is this
framework repository:

- choose the actual project directory as `--root`, rather than creating a
  working experiment under `examples/` or alongside the skill;
- do not copy local experiment history into this framework automatically;
- share only synthetic or explicitly approved example material.

Publication, deployment, and production changes require their own project
workflow and explicit authorization.

## Before creating a new experiment

1. Determine the parent directory. If it is not given, use the current working
   directory, unless it is the framework repository itself; then ask for or
   identify the actual experiment workspace.
2. Inspect its listing and read only applicable local instructions
   (`AGENTS.md`, `CLAUDE.md`, and the project `README.md` when needed). Load
   deeper project context only when a concrete action or ambiguity requires it.
   Local rules take precedence; if they conflict with the generator, preserve
   their meaning and create the equivalent minimal structure manually.
3. Obtain or safely infer:
   - a title;
   - one primary question, or at most three tightly related questions;
   - what is in scope and out of scope;
   - a testable working hypothesis, or an explicit exploratory mode.
4. Do not invent an owner, ID, source, measured value, or publication target.
   Ask when a missing value would change the experiment's meaning. Unknown
   operational details may be stated honestly as not yet settled.

A preregistered task experiment additionally requires a concrete ID, area,
owner, question, scope, and publication target. Its initial phase is
`discovery`, not `in progress` or completed.

## Create the scaffold

Run the bundled generator from the directory of the loaded skill:

```bash
python3 <skill-dir>/scripts/create_experiment.py \
  --root "<parent-directory>" \
  --title "<title>" \
  --question "<research question>" \
  --hypothesis "<testable hypothesis or explicit exploratory mode>" \
  --in-scope "<what is examined>" \
  --out-of-scope "<what the result will not prove or change>"
```

Repeat `--question` for another tightly related question. Optional flags include
`--slug`, `--next-step`, and the evaluation-contract fields; use `--help` for
the full interface. For preregistration, pass `--preregistered` together with
`--experiment-id`, `--area`, `--owner`, and `--publication-target`.

The generator:

- uses the local date and `YYYY-MM-DD_slug` (the slug is ASCII kebab-case);
- refuses an existing target and never overwrites it;
- creates only meaningful `README.md`, `OUTCOME.md`, and `.gitignore` files;
- does not create `STATE.json` before a first evolving canonical artifact or
  promotion exists;
- creates no empty directories and no `HOW_TO_USE.md`;
- leaves no `{{...}}` template placeholders.

Add any known local facts after creation, then validate. Use the same validation
after working in an existing experiment:

```bash
python3 <skill-dir>/scripts/validate_experiment.py "<experiment-path>"
```

Fix errors caused by the current work. Report pre-existing failures that are
outside scope instead of silently rewriting unrelated history. Claim only the
commands and checks that actually ran.

## One owner per document

| document | sole role |
|---|---|
| `README.md` | question, scope, current state, navigation, and reproduction |
| `OUTCOME.md` | durable answer synthesis; one `##` section per question |
| `STATE.json` | optional machine-readable pointer to the current run, current artifacts, next action, and blockers |
| `DECISION.md` | a decision supported by evidence; create only after a decision |
| `runs/INDEX.md` | readable index of every run and its epistemic authority |
| `handoff/README.md` | publication contract |
| `handoff/PUBLISHED.md` | append-only receipt of real publications |

Do not duplicate a role in another file. Do not create names such as
`*-final.md`, `latest-*`, `new-*`, or `*-summary-2.md`.

## Non-negotiable invariants

- The initial scaffold is minimal; create a directory only with its first real
  content.
- A raw snapshot is immutable while active and `src/` never mutates it in
  place. Replace it only by promoting a verified new snapshot. A retired raw
  snapshot may be pruned only when nothing current or published depends on it
  and its identity and retirement reason are recorded.
- Every attempt gets a new `runs/YYYYMMDD-HHMMSS_slug/` identity. Its original
  receipt is immutable; later authority/retention transitions name their reason
  and replacement. Bulky payloads may be pruned after promotion or rejection,
  with the minimum retained evidence determined by future use.
- Current canonical data and code use stable semantic paths. Promote a verified
  candidate atomically, update its hashes and provenance, then retire the old
  bytes. Never edit a run directory to masquerade as the new authority.
- In Czech experiment documents, label an unsupported factual claim
  `bez zdroje`, an inference `odvozené`, and material uncertainty `nejisté`.
  Every answered question includes a self-check.
- The experiment remains resumable without chat; README always names one
  concrete next step.
- Never publish or transfer anything to another knowledge base automatically.
- In synchronized directories, physical `node_modules`, virtual environments,
  and agent worktrees live outside the synchronized tree and are linked in.

## Automation boundaries

- The generator guarantees the initial shape, not the substantive quality of
  the question, hypothesis, scope, or evaluation contract.
- The validator finds structural errors, placeholders, some broken links,
  naming violations, and—when `STATE.json` exists—current-artifact path and hash
  drift. It does not decide whether a candidate deserves promotion or whether a
  retired artifact still has legal, audit, or scientific value.
- The generator does not inspect the project, move data, run an experiment, or
  publish anything. The agent remains responsible for those actions under the
  current request and local instructions.

## Load detailed guidance only when needed

Basic scaffolding and orientation need no further context. Read
[references/experiment-contract.md](references/experiment-contract.md) when the
current work creates or changes the first input, intermediate, canonical
artifact, state file, script, run, report, decision, publication, heavy
directory, promotes a candidate, prunes data, or closes a work session.
